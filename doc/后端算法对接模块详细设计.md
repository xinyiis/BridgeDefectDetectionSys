## 1. 模块概述

### 1.1 目标

在现有单图检测基础上，新增**离线视频分析能力**。

本模块的业务边界是：

- 用户上传一段本地视频文件
- 后端按帧分析该视频
- 前端接收逐帧处理结果和任务进度
- 系统将同一视频内确认后的缺陷沉淀为桥梁历史缺陷

**本模块不承担真实 RTSP/无人机直播流接入能力。**

| 模式 | 入口 | 流程 |
|------|------|------|
| **单图检测** (已有) | `POST /detection/upload` | 上传图片 → 检测 → 返回结果 |
| **视频分析任务** (新增) | `POST /detection/video/upload` | 上传视频 → 保存文件 → 返回 `task_id` |
| **视频分析执行** (新增) | `POST /detection/video/:task_id/start` + `GET /detection/video/ws` | 用户启动任务 → 建立分析会话 → 后端按帧分析 → 推送处理结果与进度 |

### 1.2 业务目标

前端需要的是“上传后尽快看到分析过程与结果”的体验，而不是等整段视频分析完成再一次性返回：

1. 用户先上传视频文件
2. 后端只保存视频并返回 `task_id`
3. 前端点击“开始分析”
4. 前端调用 `start` 接口，获取 `session_id`
5. 前端建立 WebSocket 连接
6. **只有 WebSocket 连上之后，后端才真正开始逐帧处理**
7. 每处理完一帧，就把**处理后的画面**和当前进度推给前端
8. 前端连续刷新画面，看到回放式的逐帧分析预览

### 1.3 业务约束

为了避免把桥梁历史缺陷做脏，本模块必须同时满足以下约束：

1. **同一物理缺陷不能按帧重复写入历史缺陷**
2. **历史缺陷必须保留可回看的证据图，不得引用会被清理的临时帧**
3. **视频任务状态必须持久化，不能只放内存**
4. **量化结果必须区分“精确测量”和“框级估算”，不能混用**
5. **前端逐帧预览与历史缺陷沉淀是两套不同语义**

### 1.4 支持的病害类别

| class_idx | class_name | 中文 |
|-----------|------------|------|
| 0 | Crack | 裂缝 |
| 1 | Breakage | 破损 |
| 2 | Comb | 剥落 |
| 3 | Hole | 孔洞 |
| 4 | Reinforcement | 钢筋外露 |
| 5 | Seepage | 渗水 |

### 3.2 关键设计原则

#### 原则 1：上传不处理

上传接口只做：
- 保存视频文件
- 创建任务记录
- 返回 `task_id`

**不做**：
- 不提帧
- 不调用 Python
- 不做任何检测

#### 原则 2：开始分析才处理

用户点击开始分析后：
- 前端调用 `start` 接口
- 后端返回 `session_id`
- 前端建立 WebSocket
- **WebSocket 连接成功后，后端才启动处理 goroutine**

#### 原则 3：WebSocket 只是结果流，不承担上传职责

HTTP 负责上传和状态切换，WebSocket 负责：
- 推送处理后画面
- 推送缺陷信息
- 推送进度
- 推送完成/错误状态

```go
func CalculatePhysicalDimensions(
    coords [4]float64,
    imgW, imgH int,
    pixelRatio float64,
) (x, y, w, h int, length, width, area float64) {
    w = int(coords[2] * float64(imgW))
    h = int(coords[3] * float64(imgH))
    x = int((coords[0] - coords[2]/2) * float64(imgW))
    y = int((coords[1] - coords[3]/2) * float64(imgH))

    width = float64(h) * pixelRatio

    return
```

### 4.3 追加到 `python_service_http.go`

三个新方法统一走 `multipart/form-data`：

```go
func (s *HTTPPythonService) Detect(imagePath string, req *DetectRequest) (*DetectResult, error) {
    file, err := os.Open(imagePath)
    if err != nil {
        return nil, fmt.Errorf("打开图片失败: %w", err)
    }
    defer file.Close()

    body := &bytes.Buffer{}
    writer := multipart.NewWriter(body)

    part, _ := writer.CreateFormFile("file", filepath.Base(imagePath))
    io.Copy(part, file)

    if req.ModelName != "" {
        writer.WriteField("model_name", req.ModelName)
    }
    if req.Conf > 0 {
        writer.WriteField("conf", fmt.Sprintf("%.2f", req.Conf))
    }
    writer.Close()

    httpReq, _ := http.NewRequest("POST", s.baseURL+"/algo/detect", body)
    httpReq.Header.Set("Content-Type", writer.FormDataContentType())

    resp, err := s.client.Do(httpReq)
    if err != nil {
        return nil, fmt.Errorf("调用检测接口失败: %w", err)
    }
    defer resp.Body.Close()

    if resp.StatusCode != http.StatusOK {
        bodyBytes, _ := io.ReadAll(resp.Body)
        return nil, fmt.Errorf("检测接口返回错误: %d %s", resp.StatusCode, string(bodyBytes))
    }

    var result DetectResult
    if err := json.NewDecoder(resp.Body).Decode(&result); err != nil {
        return nil, fmt.Errorf("解析检测响应失败: %w", err)
    }

    return &result, nil
}
```

## 5. 视频处理实现方案

### 5.1 总体思路

离线视频分析分五步：

1. **HTTP 上传视频**：上传视频、验证权限、生成 `task_id`
2. **HTTP 启动任务**：前端点击开始分析后调用 `start`，生成 `session_id`
3. **增量提帧与逐帧检测**：WebSocket 连接成功后，后端边提帧边分析，并维护活跃缺陷轨迹
4. **证据留存与历史沉淀**：逐帧观测入 `defect_observations`，确认后的缺陷写入 `defects`
5. **WebSocket 推送结果**：推送处理后画面、当前帧结果、任务进度、最终汇总

### 5.2 为什么不能只用普通 REST

如果只用 `POST /detection/video` 同步等待，问题有：

- 视频处理时间长，HTTP 请求容易超时
- 前端无法实时看到处理过程
- 用户体验差，只能转圈等待
- 无法展示逐帧分析过程
- 无法把“上传”和“开始分析”严格拆开
- 无法在分析过程中取消任务、恢复状态或重连查看进度

因此视频模块必须采用：

```
HTTP 上传任务 + HTTP 启动分析 + WebSocket 结果推送
```

### 5.3 视频处理主流程

```go
1. 前端上传视频文件，创建任务
2. 后端保存视频文件到 uploads/videos/
3. 后端创建持久化任务记录，状态 = uploaded
4. 前端点击“开始分析”，调用 start 接口
5. 后端生成 session_id，状态 = ready_to_process
6. 前端带 task_id + session_id 建立 WebSocket
7. WebSocket 连接成功后，后端启动 goroutine 处理该视频
8. FFmpeg 以增量方式按固定间隔输出帧图片
9. 对每一帧：
   - 调用 pythonService.Detect()
   - 保存当前帧级观测到 defect_observations 表
   - 基于当前帧结果匹配 active tracks
   - 未匹配成功则创建 candidate track
   - 命中阈值后再确认历史缺陷并写入/更新 defects 表
   - 可选调用 pythonService.Segment()
   - 生成当前帧的处理后画面
   - 若该帧是当前轨迹的最佳证据帧，则持久化保存证据图
   - 通过 WebSocket 推送给前端
10. 所有帧处理完后，关闭未完成轨迹并更新任务汇总
11. 发送 completed 消息
12. 清理临时帧文件（不清理已持久化证据图）
```

### 5.4 FrameExtractor 设计

**文件**: `pkg/video/frame_extractor.go`

```go
type FrameExtractor struct {
    ffmpegPath string
}

func NewFrameExtractor(ffmpegPath string) *FrameExtractor {
    if ffmpegPath == "" {
        ffmpegPath = "ffmpeg"
    }
    return &FrameExtractor{ffmpegPath: ffmpegPath}
}

// ExtractFramesStream 按 FPS 增量提取视频帧
// 每生成一帧就回调一次，避免“整段视频先拆完帧才开始分析”
func (e *FrameExtractor) ExtractFramesStream(
    videoPath, outputDir string,
    fps float64,
    onFrame func(framePath string, frameNo int) error,
) error {
    if fps <= 0 {
        fps = 1
    }

    if err := os.MkdirAll(outputDir, 0755); err != nil {
        return fmt.Errorf("创建帧目录失败: %w", err)
    }

    outputPattern := filepath.Join(outputDir, "frame_%06d.jpg")

    cmd := exec.Command(
        e.ffmpegPath,
        "-i", videoPath,
        "-vf", fmt.Sprintf("fps=%.2f", fps),
        "-q:v", "2",
        "-start_number", "1",
        outputPattern,
    )

    if err := cmd.Start(); err != nil {
        return fmt.Errorf("启动 FFmpeg 失败: %w", err)
    }

    frameNo := 1
    for {
        framePath := filepath.Join(outputDir, fmt.Sprintf("frame_%06d.jpg", frameNo))
        if _, err := os.Stat(framePath); err == nil {
            if err := onFrame(framePath, frameNo); err != nil {
                _ = cmd.Process.Kill()
                _ = cmd.Wait()
                return err
            }
            frameNo++
            continue
        }

        if cmd.ProcessState != nil && cmd.ProcessState.Exited() {
            break
        }

        time.Sleep(100 * time.Millisecond)
    }

    if err := cmd.Wait(); err != nil {
        return fmt.Errorf("FFmpeg 提帧失败: %w", err)
    }

    return nil
}
```

### 5.5 缺陷去重与轨迹确认设计

对于**同一段连续视频**，不能把每一帧的检测结果都直接写成一条历史缺陷，否则会出现同一个裂缝在 100 帧里生成 100 条缺陷记录的问题。

因此视频模块采用：

```text
逐帧检测（Detect/Segment）
    ↓
轨迹匹配（Tracking）
    ↓
阈值确认（Dedup Confirmation）
    ↓
写入历史 defects 表
```

#### 设计目标

在同一 `bridge_id`、同一 `task_id` 的连续视频任务内，将一组时空连续、类别一致的检测结果，判定为**同一个物理缺陷的同一条轨迹**。

这样：

- WebSocket 仍然可以逐帧返回当前画面和当前帧检测结果
- 历史缺陷表只记录“确认后的缺陷”，避免重复爆炸
- 前端统计与最终报告更接近真实物理缺陷数量

```go
    LastSeenFrame      int
    Hits               int
    Misses             int

    LastBBox           dto.VideoBBox
    BestBBox           dto.VideoBBox
    BestConfidence     float64
    AvgConfidence      float64
    BestFramePath      string

    LastMaskBase64     string
    AppearanceFeature  []float64

    DefectID           *uint
}
```

说明：

- `candidate`：刚出现的候选缺陷，还不能认定为历史缺陷
- `confirmed`：连续命中达到阈值，已确认并写入 `defects` 表
- `closed`：连续丢失超过阈值，轨迹关闭
- `DefectID`：若已确认，对应历史缺陷表中的主键，后续只更新不新增

### 5.7 同一物理缺陷的判定规则

#### 硬条件

必须同时满足：

1. `bridge_id` 相同
2. `task_id` 相同
3. `defect_type` 相同
4. 时间间隔不超过 `max_gap_frames`

不同视频任务之间，**默认不自动合并**，避免跨巡检误判。

#### 空间与外观匹配指标

建议组合判断，而不是只看一个 IoU：

1. **BBox IoU**
   - 一般目标：`IoU > 0.4`
   - 裂缝等细长目标：可放宽到 `IoU > 0.3`

2. **中心点距离**
   - 中心点距离小于图像宽高的 `5% ~ 8%`
   - 解决轻微抖动和小范围位移

3. **尺寸变化约束**
   - 宽/高比例应在 `0.5 ~ 2.0`
   - 避免把尺寸突变的目标误认为同一缺陷

4. **外观相似度**
   - 推荐对 bbox 裁剪区域提取轻量特征
   - MVP 可先留接口，后续升级为颜色直方图 / ORB / patch embedding

5. **Mask IoU（启用分割时）**
   - 若开启 SAM，优先比较 mask 重叠程度
   - 对裂缝、剥落等不规则目标更可靠

#### 推荐打分公式

```text
score =
0.35 * iou
+ 0.25 * center_similarity
+ 0.15 * size_similarity
+ 0.15 * appearance_similarity
+ 0.10 * mask_similarity
```

判定规则：

- `score > 0.65`：认为是同一缺陷
- `0.45 ~ 0.65`：继续观察，先不合并
- `< 0.45`：视为新轨迹

### 5.8 确认阈值与去重策略

为了过滤偶然误检，轨迹不能一出现就落库，必须先经过确认。

推荐确认规则：

- 连续命中至少 `3` 帧；或
- 最近 `5` 帧里命中至少 `4` 次；且
- 平均置信度 `> 0.7`

推荐关闭规则：

- 连续丢失超过 `max_misses = 3` 帧，则关闭轨迹

业务语义：

- `candidate` 阶段：只存在于内存轨迹中，不写历史缺陷
- 首次达到确认阈值：创建 1 条历史缺陷记录
- 后续继续命中：只更新这条历史缺陷的最佳证据帧、统计信息或最终结果，不新增记录

### 5.9 三档实现策略

#### 档 1：MVP（当前推荐）

规则：

- 同一 `task_id`
- 同一 `bridge_id`
- 同一 `defect_type`
- `IoU > 0.3` **或** 中心点距离小于阈值
- 连续命中至少 `3` 帧才确认

优点：

- 实现快
- 足以避免“一段视频生成大量重复缺陷”的核心问题

缺点：

- 镜头移动明显时，误判率会升高

#### 档 2：推荐版（上线演示）

在 MVP 基础上增加：

- 外观相似度
- 尺寸变化约束
- `mask IoU`
- Kalman Filter 预测轨迹位置

#### 档 3：增强版（更接近物理缺陷级识别）

在推荐版基础上增加：

- 帧间对齐 / 视频稳像
- ORB/SIFT + RANSAC 单应矩阵
- 构件区域定位
- 3D 模型或桥面坐标投影

### 5.10 为什么只靠 bbox 不够

视频不是静态图，实际场景里会出现：

- 无人机/相机移动
- 镜头抖动
- 视角变化
- 缩放变化
- 桥面纹理相似

如果只写“同类别 + IoU > 0.4”，会出现两类问题：

1. 明明是同一个裂缝，却因镜头移动被误判成新缺陷
2. 明明是不同裂缝，却因位置接近被错误合并

因此必须增加：

- 时间连续性
- 尺寸约束
- 外观相似性
- 可选的 `mask IoU`

### 5.11 相机运动场景的增强建议

真正的难点是：**相机在动，像素坐标也在动**。

如果项目后续需要更高可靠性，建议增加“帧间对齐”能力：

```text
当前帧 -> 与上一帧做特征点匹配 -> 估计单应矩阵 -> 映射到参考坐标系 -> 再比较轨迹位置
```

可选实现：

- ORB/SIFT 特征点匹配
- RANSAC 求 Homography
- 将当前 bbox 映射到参考帧坐标后，再计算 IoU / 中心距离

第一版设计中，这部分作为**增强能力预留**，不纳入 MVP 必做范围。

### 5.12 任务持久化模型设计

视频分析任务不能只存在 `sync.Map` 内存里，否则页面刷新、进程重启、管理员查询都会丢状态。

因此需要新增持久化表 `video_analysis_tasks`：

### 5.16 量化口径设计

视频分析里的长度、宽度、面积不能一律直接从 bbox 得出再当成正式历史值。

统一规则：

1. **Detect 阶段**
   - bbox 仅用于定位与跟踪
   - 可计算 `bbox_estimate` 供前端实时预览
   - 不应直接作为正式面积统计口径

2. **Segment 阶段**
   - 若成功返回 mask，则长度/宽度/面积以 mask 量化为准
   - 这时 `MeasurementSource = segment`
   - `MeasurementStatus = measured`

3. **未启用或分割失败**
   - 历史缺陷允许保存，但量化字段标记为估算或待测
   - `MeasurementSource = bbox_estimate`
   - `MeasurementStatus = estimated`

因此前端与报表必须区分：

- 实时画面区：可显示“估算尺寸”
- 历史缺陷/报表：优先显示“精确测量值”，没有则明确标记“估算”

### 5.19 单帧处理与轨迹更新逻辑

```go
_ = uc.frameExtractor.ExtractFramesStream(task.VideoPath, tempDir, task.FPS, func(framePath string, frameNo int) error {
    detectResult, err := uc.pythonService.Detect(framePath, &service.DetectRequest{
        ModelName: task.ModelName,
        Conf:      0.25,
    })
    if err != nil {
        // 发 error 消息，可按策略继续下一帧或终止任务
        return nil
    }

    // 获取帧尺寸
    imgW, imgH, _ := getImageDimensions(framePath)

    defects := make([]dto.VideoFrameDefect, 0, len(detectResult.YOLOBBoxes))

    for _, bbox := range detectResult.YOLOBBoxes {
        x, y, w, h, estLength, estWidth, estArea := service.CalculatePhysicalDimensions(
            bbox.YOLOCoords, imgW, imgH, task.PixelRatio,
        )

        currentDefect := dto.VideoFrameDefect{
            DefectType: service.ClassNameToChinese[bbox.ClassIdx],
            BBox: dto.VideoBBox{X: x, Y: y, Width: w, Height: h},
            Length: estLength,
            Width:  estWidth,
            Area:   estArea,
            MeasurementSource: "bbox_estimate",
            MeasurementStatus: "estimated",
        }

        // 每帧观测先写 observation，供证据回放和缺陷详情使用
        _ = uc.observationRepo.Create(&model.DefectObservation{
            TaskID:      task.TaskID,
            BridgeID:    task.BridgeID,
            FrameNo:     frameNo,
            TimestampMS: int(float64(frameNo-1) / task.FPS * 1000),
            DefectType:  currentDefect.DefectType,
            BBox:        currentDefect.BBox.JSON(),
            Confidence:  bbox.Confidence,
            FramePath:   framePath,
        })

        // 先做轨迹匹配，不直接写历史 defects 表
        track, matched := uc.matchActiveTrack(task.TaskID, currentDefect)
        if matched {
            uc.updateTrack(track, currentDefect, framePath)
        } else {
            track = uc.createCandidateTrack(task, currentDefect, framePath)
        }

        // 达到确认阈值时首次落库
        if uc.shouldConfirmTrack(track) && track.DefectID == nil {
            defect := &model.Defect{
                BridgeID:   task.BridgeID,
                DefectType: track.DefectType,
                ImagePath:  track.BestFramePath,
                ResultPath: track.BestResultPath,
                BBox:       fmt.Sprintf(`{"x":%d,"y":%d,"width":%d,"height":%d}`,
                    track.BestBBox.X, track.BestBBox.Y, track.BestBBox.Width, track.BestBBox.Height),
                Length:     track.FinalLength,
                Width:      track.FinalWidth,
                Area:       track.FinalArea,
                Confidence: track.BestConfidence,
                DetectedAt: time.Now(),
                SourceType: "video",
                SourceTaskID: &task.TaskID,
                TrackID: &track.TrackID,
                FirstSeenAt: &track.FirstSeenAt,
                LastSeenAt: &track.LastSeenAt,
                ObservationCount: track.Hits,
                BestFramePath: track.BestFramePath,
                BestResultPath: track.BestResultPath,
                MeasurementSource: track.MeasurementSource,
                MeasurementStatus: track.MeasurementStatus,
            }
            created, _ := uc.defectService.ConfirmVideoDefect(defect)
            track.DefectID = &created.ID
            track.Status = TrackConfirmed
            task.TotalDefects++
        } else if track.DefectID != nil {
            _ = uc.defectService.UpdateVideoDefectEvidence(*track.DefectID, &service.DefectEvidenceUpdate{
                LastSeenAt:        track.LastSeenAt,
                ObservationCount:  track.Hits,
                BestFramePath:     track.BestFramePath,
                BestResultPath:    track.BestResultPath,
                BestConfidence:    track.BestConfidence,
                FinalLength:       track.FinalLength,
                FinalWidth:        track.FinalWidth,
                FinalArea:         track.FinalArea,
                MeasurementSource: track.MeasurementSource,
                MeasurementStatus: track.MeasurementStatus,
            })
        }

        defects = append(defects, currentDefect)
    }

    // 结果画面优先级：segment fusion_image > detect image_results
    var outputImageBase64 string
    if task.EnableSegment && len(detectResult.YOLOBBoxes) > 0 {
        bboxesJSON, _ := json.Marshal(detectResult.YOLOBBoxes)
        segResult, err := uc.pythonService.Segment(framePath, &service.SegmentRequest{
            BBoxesJSON: string(bboxesJSON),
            Alpha:      0.5,
        })
        if err == nil {
            outputImageBase64 = segResult.FusionImage
            uc.applySegmentMeasurements(tracks, segResult, task.PixelRatio)
        }
    }
    if outputImageBase64 == "" {
        outputImageBase64 = detectResult.ImageResult
    }

    persistedResultPath := uc.saveBestEvidenceIfNeeded(task, framePath, outputImageBase64, tracks)

    _ = send(dto.VideoFrameMessage{
        Type:            "frame",
        TaskID:          task.TaskID,
        SessionID:       task.SessionID,
        FrameNo:         frameNo,
        ProcessedFrames: task.ProcessedFrames,
        TotalFrames:     task.TotalFrames,
        Progress:        currentProgress(task),
        TimestampMS:     int(float64(frameNo-1) / task.FPS * 1000),
        ImageBase64:     outputImageBase64,
        PersistedResultPath: persistedResultPath,
        Defects:         defects,
        DefectCount:     len(defects),
    })
    return nil
})
```

## 7. 前端对接方案

### 7.1 前端完整流程

```js
// Step 1: 上传视频（仅上传，不处理）
const formData = new FormData()
formData.append('video', file)
formData.append('bridge_id', bridgeId)
formData.append('pixel_ratio', pixelRatio)
formData.append('fps', 1)
formData.append('enable_segment', true)

const uploadResp = await axios.post('/api/v1/detection/video/upload', formData, {
  withCredentials: true,
})

const { task_id } = uploadResp.data.data

// Step 2: 用户点击开始分析，创建分析会话
const startResp = await axios.post(`/api/v1/detection/video/${task_id}/start`, {}, {
  withCredentials: true,
})

const { session_id } = startResp.data.data

// Step 3: 建立 WebSocket，连接成功后后端才开始处理
const ws = new WebSocket(
  `ws://localhost:8080/api/v1/detection/video/ws?task_id=${task_id}&session_id=${session_id}`
)

// Step 4: 实时接收处理后帧
ws.onmessage = (event) => {
  const message = JSON.parse(event.data)

  if (message.type === 'frame') {
    currentFrameUrl.value = `data:image/jpeg;base64,${message.image_base64}`
    progress.value = message.progress
    currentDefects.value = message.defects
  }

  if (message.type === 'completed') {
    summary.value = message.defect_summary
  }

  if (message.type === 'error') {
    errorMessage.value = message.message
  }
}
```

### 7.2 前端页面展示建议

页面建议拆成三块：

1. **视频上传区**
   - 选择视频文件
   - 设置桥梁、像素系数、fps、是否启用分割
   - 点击“上传视频”

2. **任务控制区**
   - 点击“开始分析”
   - 点击“取消任务”
   - 建立 WebSocket
   - 显示任务状态与连接状态

3. **逐帧预览区 + 结果区**
   - 显示当前处理后的帧图像
   - 显示进度条
   - 显示当前帧缺陷列表
   - 显示最终已确认缺陷统计

### 7.3 为什么前端能“看起来像视频”

虽然底层不是传统 HLS/RTMP 视频流，而是：

```
一帧一帧的 Base64 图片通过 WebSocket 推送
```

但前端只要连续刷新 `<img src="data:image/jpeg;base64,...">`，用户看到的效果就是连续更新的处理后画面。

同时需要注意两层语义：

1. 画面层：前端看到的是**每一帧当前检测结果**
2. 业务层：后端落库的是**经跟踪与去重确认后的历史缺陷**

也就是说：

- 前端可以在第 1 帧就看到一个候选裂缝框
- 但后端不会在第 1 帧就立刻写入历史缺陷
- 只有该裂缝在后续连续命中达到阈值后，才会被确认成真正缺陷记录

这样既保证逐帧观感，也避免数据库里出现大量重复缺陷。

这对离线视频分析和比赛演示足够，而且实现难度远低于真正的视频编码推流。

### 8.3 风险与对策

| 风险 | 说明 | 对策 |
|------|------|------|
| FFmpeg 不存在 | 后端机器未安装 FFmpeg | 启动时检查依赖 |
| WebSocket 断开 | 前端页面刷新或网络断开 | 任务继续执行，状态仍以数据库为准，前端可重连查询 |
| 视频太大 | 帧数过多处理慢 | 限制大小 + 降低 fps |
| SAM 太慢 | 开启分割后耗时明显增加 | 默认关闭，只在需要时启用 |
| Base64 太大 | 单帧图片消息过大 | 提帧时控制分辨率 / JPEG 质量 |
| 重复 start | 已创建会话又重复调用 start | 限制只有 `uploaded` 状态允许 start |
| 历史缺陷证据失效 | 临时帧被清理后历史记录无法回看 | 最佳证据帧与处理后图持久化保存 |
| 量化口径失真 | bbox 估算被误当正式面积 | 增加 measurement_source / measurement_status |
| 任务状态丢失 | 进程重启后无法恢复 | 任务状态持久化到 `video_analysis_tasks` |

## 总结

### 设计原则

1. **单图模块不动** —— 现有缺陷检测代码和测试完全不受影响
2. **视频模块独立新增** —— 上传和启动分析严格拆开
3. **启动分析才处理** —— 不再是上传后后台自动跑
4. **逐帧结果可见** —— 每一帧处理后立刻推送给前端
5. **结果与历史分层** —— 帧级观测和历史缺陷分开存储
6. **历史缺陷先跟踪再确认** —— 同一视频内通过检测 + 跟踪 + 去重确认，避免重复落库
7. **任务真相以数据库为准** —— 运行态内存只是缓存，不是系统记录
8. **量化结果分级展示** —— 估算值和精确测量值严格区分

### 最终方案

- 保留已有：`POST /api/v1/detection/upload`
- 新增：`POST /api/v1/detection/video/upload`
- 新增：`POST /api/v1/detection/video/:task_id/start`
- 新增：`GET /api/v1/detection/video/:task_id`
- 新增：`POST /api/v1/detection/video/:task_id/cancel`
- 新增：`GET /api/v1/detection/video/ws`
- 输出效果：前端看到回放式的逐帧分析结果和任务进度
- 数据语义：数据库只保存经轨迹确认后的历史缺陷，不按帧重复写入
- 证据策略：历史缺陷必须引用已持久化保存的最佳证据图，不能引用临时帧路径
