# 视频算法异步对接最终实施方案

## 1. 文档目标

本文档用于固化视频检测链路的最终实施方案，明确后端与算法端的职责边界、接口协议、状态机、数据流、入库策略与实施阶段。

本次最终结论以以下边界为准：

- **抽帧由后端负责**
- **后端负责逐帧派发 detect 任务**
- **算法端只负责消费帧级 detect 请求并异步返回结构化结果**
- **视频链路只做 detect，不做 segment**
- **后端先写帧级观测，再做聚合，最后只对关键帧做正式缺陷入库**

本文档聚焦视频异步检测方案，不改变当前单图检测接口的既有语义。

---

## 2. 背景与问题

当前单图链路已经证明：

- 算法核心推理时间不等于端到端总耗时
- 视频场景的瓶颈不只是单帧推理，而是“抽帧、派发、排队、推理、回调、聚合、入库”整条链路
- 如果视频链路继续使用同步串行模式，后端会被算法耗时阻塞，前端也无法实时感知进度

因此视频链路需要从“同步逐帧处理”改为“后端抽帧 + 帧任务异步派发 + 结果异步回调 + 后端聚合入库”的模式。

同时，结合后续部署规划：

- 后端与算法模块未来会放到同一服务器、同一环境
- 两者可以共享本地磁盘、本地网络与统一运维资源
- 但设计上仍要保留未来扩展到跨机部署的空间

---

## 3. 最终方案结论

采用以下固定架构：

### 3.1 核心原则

- 视频由后端统一接收并保存
- 后端按 `1 秒 1 帧` 抽帧
- 后端将抽出的帧作为 detect 任务派发给算法端
- 算法端只执行 `detect only`
- 算法端不返回 Base64 图片、不返回渲染图，只返回结构化检测结果
- 后端接收帧结果后先写 `DefectObservation`
- 后端基于时间与空间相似性聚合候选轨迹
- 每个候选事件只选择一个关键帧写入正式 `Defect`
- 前端使用播放延迟缓冲，不要求模型追逐实时当前帧

### 3.2 本方案的最终定位

视频链路的默认产物不是正式缺陷，而是“观测结果”。

正式缺陷只来源于关键帧确认，不来源于全部命中帧。

视频检测承担的是：

- 发现
- 定位
- 候选事件确认

不承担：

- 精细分割
- 高精度几何测量
- 每帧正式缺陷入库

---

## 4. 职责边界

## 4.1 后端负责

后端负责完整的视频任务编排和业务落库，具体包括：

- 用户鉴权
- 视频上传入口
- 保存视频元数据
- 创建视频任务与状态管理
- 将视频保存到共享目录或算法端可访问路径
- 按配置抽帧
- 创建帧级 detect 请求
- 控制帧任务派发并发和积压上限
- 接收算法异步回调结果
- 写入 `DefectObservation`
- 聚合候选轨迹
- 选择关键帧
- 写入正式 `Defect`
- WebSocket 推送任务进度和检测结果
- 处理幂等、失败重试、收尾和清理

## 4.2 算法端负责

算法端只承担 detect worker 角色，具体包括：

- 接收帧级 detect 请求
- 校验帧引用可访问性
- 将请求写入算法侧内部队列
- 后台 worker 消费请求
- 对每一帧执行 `detect`
- 返回结构化结果与阶段耗时
- 失败时明确返回错误状态
- 支持取消、重试与回调失败重发

## 4.3 明确不再采用的模式

本方案明确不采用以下模式：

- 算法端接收完整视频后自行抽帧
- 视频链路返回 Base64 图片
- 视频链路中调用 `segment`
- 每一帧命中直接写正式 `Defect`
- 上传接口同步等待整个视频分析完成

## 5. 推荐部署与传输方式

## 5.1 当前推荐部署方式

后端与算法端后续部署在同一服务器时，建议采用：

- 后端服务进程
- 算法服务进程
- 共享本地目录
- 本机内网 HTTP 调用
- 后端回调地址使用内网地址或 localhost 可达地址

## 5.2 共享目录建议

建议统一使用共享工作目录：

```text
/data/bridge_detect/
  videos/
    {task_id}.mp4
  frames/
    {task_id}/
      frame_000001.jpg
      frame_000002.jpg
  keyframes/
    {task_id}/
  logs/
```

说明：

- 原视频保存在 `videos/`
- 抽帧保存在 `frames/{task_id}/`
- 被选为最佳关键帧的图片保存在 `keyframes/{task_id}/`
- 数据库中建议同时记录：
  - `absolute_path`
  - `relative_path`

## 5.3 为什么采用共享路径

当后端与算法同机时，最优方式不是重复上传帧图，而是：

- 后端抽帧落共享目录
- 帧任务只传 `frame_ref`
- 算法端直接读取本地文件

这样可以：

- 避免逐帧传图的序列化和网络开销
- 降低重复落盘
- 便于失败重试和审计追溯

---

## 6. 总体调用流程

## 6.1 主流程

```text
前端
  -> 上传视频到后端

后端
  -> 保存视频元数据
  -> 创建 video_task
  -> 按 1 秒 1 帧抽帧
  -> 为每一帧创建 frame_request
  -> 调用算法 detect 异步接口
  -> 返回 task_id 给前端

算法端
  -> 接收 frame_request
  -> 写入内部队列
  -> worker 消费
  -> 执行 detect
  -> 回调后端 frame-result

后端
  -> 接收帧结果回调
  -> 更新 frame_request 状态
  -> 写 DefectObservation
  -> 聚合轨迹
  -> 推送 WebSocket
  -> 轨迹关闭时确认关键帧并正式入库

后端
  -> 全部帧派发完成并收到最终结果后
  -> 收尾未关闭轨迹
  -> 更新任务 completed
```

## 6.2 为什么仍然需要队列与异步

即使后端与算法端在同机环境，仍然需要异步和队列：

- 视频分析本质上是长任务，不适合同步等待
- 后端抽帧速度和算法消费速度不一致
- 算法端仍要控制 worker 并发，避免 GPU/CPU 被打满
- 后端上传接口不能阻塞到视频分析完成
- 前端需要基于“延迟播放 + 结果回填”模型展示

队列的核心目标是：

- 解耦后端抽帧与算法推理
- 建立背压
- 支持失败恢复
- 提供排队与耗时观测

## 7. 异步状态机设计

## 7.1 后端视频任务状态

建议视频任务状态如下：

- `uploaded`
- `frame_extracting`
- `dispatching`
- `processing`
- `completed`
- `failed`
- `cancelled`

说明：

- `uploaded`：后端已收到视频
- `frame_extracting`：后端正在抽帧
- `dispatching`：后端正在派发帧任务
- `processing`：至少已有一部分帧进入算法处理阶段
- `completed`：所有帧结果处理完成并完成收尾
- `failed`：任务失败
- `cancelled`：任务取消

## 7.2 帧请求状态

后端必须引入帧级请求状态表或等价持久化模型。

建议至少包含：

- `request_id`
- `task_id`
- `frame_no`
- `timestamp_ms`
- `frame_ref`
- `status`
- `queued_at`
- `started_at`
- `finished_at`
- `queue_latency_ms`
- `detect_total_ms`
- `decode_ms`
- `infer_ms`
- `postprocess_ms`
- `error_message`
- `retry_count`

帧状态建议为：

- `pending`
- `queued`
- `processing`
- `completed`
- `failed`
- `dead_letter`

说明：

- `pending`：后端已生成帧任务，尚未发送
- `queued`：算法端已接收并进入内部队列
- `processing`：算法端已开始处理
- `completed`：算法端返回成功结果
- `failed`：算法端返回失败或后端确认失败
- `dead_letter`：达到重试上限后转入死信

## 8. 后端与算法端接口定义

## 8.1 后端调用算法端：创建帧级 detect 任务

用途：

- 后端把单帧 detect 请求提交给算法端
- 算法端只需快速校验与入队，不做同步长时处理

建议接口：

`POST /algo/video/frames/detect`

请求体：

```json
{
  "request_id": "frame_req_123_45",
  "task_id": "video_task_123",
  "bridge_id": 101,
  "frame_no": 45,
  "timestamp_ms": 45000,
  "frame_ref": "file:///data/bridge_detect/frames/video_task_123/frame_000045.jpg",
  "model_name": "baseline",
  "conf": 0.25,
  "callback_base_url": "http://backend.internal/api/v1/detection/video/callback"
}
```

字段说明：

- `request_id`：单帧请求 ID，用于幂等和排查
- `task_id`：后端视频任务 ID
- `bridge_id`：桥梁 ID
- `frame_no`：帧序号
- `timestamp_ms`：帧在视频中的时间偏移
- `frame_ref`：算法端可访问的帧路径引用
- `model_name`：模型名称
- `conf`：置信度阈值
- `callback_base_url`：算法端回调后端的基础地址

成功响应：

```json
{
  "status": "accepted",
  "request_id": "frame_req_123_45",
  "task_id": "video_task_123",
  "queued_at": "2026-04-12T14:00:00Z"
}
```

失败响应：

```json
{
  "status": "failed",
  "request_id": "frame_req_123_45",
  "task_id": "video_task_123",
  "error_message": "frame_ref not accessible"
}
```

## 8.2 后端调用算法端：取消任务

支持两级取消：

### 取消整个视频任务

`POST /algo/video/tasks/{task_id}/cancel`

请求体：

```json
{
  "task_id": "video_task_123"
}
```

### 可选：取消单帧请求

`POST /algo/video/frames/{request_id}/cancel`

用于后端在极端场景下清理局部积压，但第一版可不实现。

## 8.3 算法端回调后端：单帧入队确认

用途：

- 算法端已真正将帧请求写入内部队列
- 后端据此把帧状态从 `pending` 更新为 `queued`

建议接口：

`POST /api/v1/detection/video/callback/frame-queued`

请求体：

```json
{
  "request_id": "frame_req_123_45",
  "task_id": "video_task_123",
  "frame_no": 45,
  "timestamp_ms": 45000,
  "status": "queued",
  "queued_at": "2026-04-12T14:00:01Z"
}
```

## 8.4 算法端回调后端：单帧开始处理

建议接口：

`POST /api/v1/detection/video/callback/frame-started`

请求体：

```json
{
  "request_id": "frame_req_123_45",
  "task_id": "video_task_123",
  "frame_no": 45,
  "timestamp_ms": 45000,
  "status": "processing",
  "started_at": "2026-04-12T14:00:05Z"
}
```

## 8.5 算法端回调后端：单帧 detect 结果

这是最核心的接口。

建议接口：

`POST /api/v1/detection/video/callback/frame-result`

成功请求体：

```json
{
  "request_id": "frame_req_123_45",
  "task_id": "video_task_123",
  "frame_no": 45,
  "timestamp_ms": 45000,
  "status": "success",
  "queue_latency_ms": 180,
  "detect_total_ms": 1500,
  "decode_ms": 120,
  "infer_ms": 1080,
  "postprocess_ms": 300,
  "frame_ref": "file:///data/bridge_detect/frames/video_task_123/frame_000045.jpg",
  "yolo_bboxes": [
    {
      "box_id": 0,
      "class_idx": 0,
      "class_name": "Crack",
      "yolo_coords": [0.51, 0.48, 0.18, 0.07],
      "confidence": 0.92
    }
  ]
}
```

失败请求体：

```json
{
  "request_id": "frame_req_123_45",
  "task_id": "video_task_123",
  "frame_no": 45,
  "timestamp_ms": 45000,
  "status": "failed",
  "error_message": "decode frame failed"
}
```

说明：

- `frame_ref` 是该帧在共享目录中的稳定路径引用
- 不返回 `image_base64`
- 不返回渲染图
- 只返回结构化 bbox 与阶段耗时

## 8.6 算法端回调后端：视频任务完成

后端完成全部帧派发后，视频任务何时进入 `completed`，需要一个整体收尾信号。

建议两种实现方式：

### 方式 A：后端自主判定（推荐第一版）

后端通过以下条件判定完成：

- 所有 `frame_request` 都进入终态（`completed/failed/dead_letter`）
- 所有未关闭轨迹已完成结算

此方式下不强依赖算法端任务完成回调。

### 方式 B：算法端补充任务完成回调（可选增强）

`POST /api/v1/detection/video/callback/task-completed`

请求体：

```json
{
  "task_id": "video_task_123",
  "status": "completed",
  "total_frames": 120,
  "processed_frames": 120,
  "failed_frames": 0,
  "completed_at": "2026-04-12T14:03:00Z"
}
```

若实现该接口，可用于更快收尾和更清晰的任务观测，但最终完成判定仍以后端数据一致性为准。

## 8.7 算法端回调后端：任务失败

建议接口：

`POST /api/v1/detection/video/callback/task-failed`

请求体：

```json
{
  "task_id": "video_task_123",
  "status": "failed",
  "error_message": "worker unavailable",
  "failed_at": "2026-04-12T14:01:10Z"
}
```

## 9. 后端回调处理逻辑

## 9.1 接收单帧结果后的处理顺序

后端处理 `frame-result` 回调时，建议严格按以下顺序：

1. 校验请求来源和签名
2. 校验 `task_id` 与 `request_id` 是否存在
3. 以 `request_id` 做幂等校验
4. 更新 `frame_request` 状态与耗时字段
5. 过滤低于 `candidate_confidence_threshold` 的 bbox
6. 写入 `DefectObservation`
7. 更新候选轨迹聚合器
8. 生成 WebSocket 事件推送前端
9. 如某轨迹在 `track_close_seconds` 内无新命中，则关闭轨迹
10. 为关闭轨迹选择关键帧
11. 将关键帧写入正式 `Defect`

## 9.2 任务完成后的收尾

当后端确认所有帧请求都进入终态后，执行以下收尾：

1. 结算所有未关闭轨迹
2. 将满足条件的候选轨迹确认入库
3. 更新任务统计字段
4. 标记任务 `completed`
5. 推送最终完成消息

## 10. 关键帧聚合与正式入库策略

## 10.1 什么是“观测”

每次抽帧 detect 命中的一个 bbox，记为一条观测：

- `task_id`
- `frame_no`
- `timestamp_ms`
- `defect_type`
- `bbox`
- `confidence`
- `frame_ref`

对应现有模型：

- `DefectObservation`

## 10.2 什么是“关键缺陷帧”

关键缺陷帧不是“所有命中帧”，而是一个聚合簇中最值得保留的那一帧。

定义建议：

- 同一缺陷类型
- 时间上连续
- 空间位置高度重叠

满足这三个条件的多帧观测，视为同一个候选缺陷事件。

## 10.3 聚合规则

建议采用简单、稳定、可解释的第一版规则：

### Rule 1：类别一致

只有 `defect_type` 相同的观测才允许聚合。

### Rule 2：时间窗口

如果两条观测时间间隔小于等于 `3 秒`，才考虑属于同一事件。

配置项：

- `video_detection.track_window_seconds: 3`

### Rule 3：位置重叠

两条观测的 bbox 计算 IoU。

阈值建议：

- `iou >= 0.3` 视为同一目标

配置项：

- `video_detection.track_iou_threshold: 0.3`

## 10.4 最佳关键帧选择规则

每个聚合簇中，选择一条观测作为正式入库帧。

优先级建议：

1. `confidence` 最高
2. bbox 面积更大
3. 更居中、更完整
4. 若仍相同，取最早观测

第一版至少实现前两条。

## 10.5 正式入库时机

建议不要每收到一帧就立即决定，而是在以下时机确认：

### 触发条件 A：轨迹结束

某个聚合簇在 `track_close_seconds` 内没有新的匹配观测，认为事件结束，触发确认入库。

### 触发条件 B：任务结束

视频处理完成后，把所有未关闭的轨迹统一结算并入库。

## 10.6 正式入库内容

正式入库时只写一条缺陷记录，来源于关键帧。

写入：

- `bridge_id`
- `defect_type`
- `image_path = best_frame_path`
- `result_path = ""` 或后续扩展
- `bbox`
- `confidence`
- `source_type = "video"`
- `source_task_id`
- `track_id`
- `first_seen_at`
- `last_seen_at`
- `observation_count`
- `best_frame_path`
- `measurement_source = "video_detect"`
- `measurement_status = "pending"`

不写：

- 长度、面积等高精度测量结果

原因：

- 视频链路不做 `segment`
- 几何测量可信度不足以伪装成正式精检结果

## 11. WebSocket 推送定义

建议视频 WebSocket 不再推图，只推结构化结果与进度。

建议消息结构：

```json
{
  "task_id": "video_task_123",
  "type": "frame_result",
  "frame_no": 45,
  "timestamp_ms": 45000,
  "progress": 0.38,
  "queue_latency_ms": 180,
  "detect_latency_ms": 1500,
  "defects": [
    {
      "class_name": "Crack",
      "confidence": 0.92,
      "yolo_coords": [0.51, 0.48, 0.18, 0.07]
    }
  ]
}
```

可推送事件类型：

- `task_started`
- `frame_result`
- `task_completed`
- `task_failed`
- `task_cancelled`

如需要，也可增加：

- `frame_queued`
- `frame_failed`

## 12. 幂等与失败重试

## 12.1 幂等要求

以下回调都必须支持幂等：

- `frame-queued`
- `frame-started`
- `frame-result`
- `task-completed`
- `task-failed`

幂等主键建议：

- 帧级事件：`request_id + event_type`
- 帧最终结果：`request_id`
- 任务级事件：`task_id + status`

后端对于重复的同一回调：

- 不重复写 `DefectObservation`
- 不重复写正式 `Defect`
- 不重复推重复的最终入库事件

## 12.2 重试要求

算法端在以下场景可重试回调：

- 后端超时
- 后端返回 `5xx`
- 网络中断

不建议在以下场景无限重试：

- 后端返回 `4xx` 且明确为请求格式错误
- `task_id` 或 `request_id` 不存在
- 签名校验失败

## 12.3 死信要求

对于单帧请求，建议后端或算法端配置最大重试次数。超过上限后：

- 标记帧状态为 `dead_letter`
- 保留错误原因
- 任务最终仍可进入 `completed`，但需在统计字段中体现失败帧数量
- 若失败比例超过阈值，可升级为任务 `failed`

## 13. 性能观测要求

为了判断瓶颈，算法端回调必须包含至少这些耗时：

- `queue_latency_ms`
- `detect_total_ms`
- `decode_ms`
- `infer_ms`
- `postprocess_ms`

后端也要记录：

- 视频上传耗时
- 抽帧总耗时
- 单帧派发耗时
- 首帧回调耗时
- 平均帧结果回调耗时
- 轨迹关闭到正式入库耗时
- 整体任务完成耗时

通过这些数据，可以把瓶颈分清楚：

- 是上传慢
- 是抽帧慢
- 是派发排队慢
- 是算法推理慢
- 还是后端聚合/入库慢

## 14. 配置项建议

建议在 `config.yaml` 中明确以下配置：

```yaml
video_detection:
  enabled: true
  sample_fps: 1
  playback_delay_seconds: 4
  dispatch_batch_size: 8
  max_queue_inflight: 8
  callback_timeout_ms: 3000
  callback_retry_times: 3
  track_window_seconds: 3
  track_close_seconds: 4
  track_iou_threshold: 0.3
  candidate_confidence_threshold: 0.45
  persist_confidence_threshold: 0.55
  shared_video_root: /data/bridge_detect/videos
  shared_frame_root: /data/bridge_detect/frames
  shared_keyframe_root: /data/bridge_detect/keyframes
  frame_retention_hours: 72
```

说明：

- `sample_fps`：视频抽帧频率，当前固定 `1`
- `playback_delay_seconds`：前端播放延迟缓冲
- `dispatch_batch_size`：后端单次批量派发帧任务数量
- `max_queue_inflight`：允许算法端同时在处理链路中的帧数上限
- `track_*`：轨迹聚合参数
- `candidate_confidence_threshold`：进入观测聚合的最低置信度
- `persist_confidence_threshold`：正式入库最低置信度
- `frame_retention_hours`：普通抽帧的保留时长

## 16. 验收标准

### 16.1 功能验收

- 用户上传视频后，后端能创建任务并完成抽帧
- 后端能将帧级任务异步派发给算法端
- 算法端能异步消费帧任务并返回结果
- 后端能收到单帧结果回调
- 后端能写帧级观测
- 同一缺陷跨多帧只形成一个正式缺陷
- WebSocket 能按时间轴回填结构化框结果

### 16.2 接口验收

- 视频链路不再返回 Base64 图片
- 视频链路只使用 `detect`
- 帧级回调接口支持幂等和失败重试
- 帧请求状态可追踪、可审计

### 16.3 性能验收

- 视频上传、抽帧、派发、detect、回调、聚合、入库各阶段耗时可拆分
- 单帧结果回调包含完整阶段耗时
- 前端在 `playback_delay_seconds` 设定范围内能稳定显示对应时刻框

## 17. 建议实施顺序

### 第一阶段：打通最小闭环

- 固化视频任务状态机
- 后端保存视频并抽帧
- 新增帧级 detect 派发接口
- 新增后端 callback handler
- 跑通“后端抽帧 + detect-only + 单帧回调”

### 第二阶段：接业务结果闭环

- 接入 `DefectObservation`
- 接入轨迹聚合与关键帧确认
- 接入正式缺陷入库

### 第三阶段：增强稳定性与可运维性

- 完善幂等和失败重试
- 完善性能打点
- 增加 TTL 清理与关键帧保留策略
- 根据真实数据调整 `playback_delay_seconds` 与 `max_queue_inflight`

---

## 18. 最终实施结论

最终实施方案明确如下：

- **视频由后端统一接收并抽帧**
- **后端按帧异步派发 detect 请求给算法端**
- **算法端只负责 detect-only 消费与结构化结果回调**
- **后端负责观测聚合、关键帧选择、正式缺陷入库与前端推送**

这是当前业务目标、部署规划和代码演进成本之间最平衡、最可执行的方案。
